Answers that show the path.

Company Brain is a Slack agent over a single FalkorDB graph. People, teams, services, documents, tickets, decisions and chat are nodes and edges; Slack and GitHub feed it live. Ask who owns billing, why a decision was made, or what breaks if auth goes down, and it answers by walking the graph, then prints the edges it used.

  • The agent never writes Cypher. It picks from a fixed catalogue of hand-written, parameterised queries.
  • The answer is the path. Every tool returns the exact edges it walked, as A -[REL]-> B.
  • It never guesses. Names resolve against the graph first; a miss returns the nearest names.
  • Permissions are a graph query. Every read is filtered by the rooms and repos the asker can see.

    Onboard your team

    Type one line in Slack. The bot shows an Approve card that counts what it will create before anything is written, and the reply cites the edges it wrote.

    onboard team: Sales | members: @priya @dev | owns: Renewals (process), HubSpot (system), Pricing playbook (playbook) | decision: annual plans only, decided 2026-09-01

    Kinds: service, system, process, product, account, policy, playbook. Writes merge by id and never delete. A larger team can be imported from a file with the same fields: the team, its members, what it owns (each with a kind and an owner), and its decisions.

    How it answers

    The design the whole project hangs on: the graph decides what the agent can know and how it explains itself.

    • A fixed tool catalogue

      Each tool is a hand-written, parameterised traversal with a JSON schema for its arguments. One structured call to Claude Haiku picks the tool and fills the arguments; a keyword router does the same job with no model, so every path works offline. No model-generated string ever reaches a query.

    • The path comes back with the answer

      Every tool returns the edges it walked. The reply prints them, names the tool, and says whether the model or the keywords picked it. Explanation is the traversal, not a sentence written afterwards.

    • Refuse to guess

      The names in a question are resolved against the graph before anything runs. A miss answers "Nothing in the graph matches" and offers the nearest candidates.

    • Decisions stay current

      A decision recorded in a channel, after approval, supersedes the one it replaces and links to the documents, tickets and pull requests it is based on. Asking about the old one answers "no longer current", then the current one, with both dates. Nothing is deleted.

    • Writes wait for a human

      Tools that write the graph never run from the loop. The turn suspends with an Approve card that names the resolved target, and the write lands only after a click.

    • Algorithms as tools

      PageRank over DEPENDS_ON ranks load-bearing services, betweenness names the connector in a blast radius, algo.SPpaths explains why two things are connected, and label propagation finds who actually works together.

    • Scopes per room

      Every node written from Slack or GitHub carries the scope of the public channel, private channel, DM or private repo it came from. Every query ends with the same filter on what the asker may read.

    • Take FalkorDB out and nothing answers

      A proof route runs the same questions with every graph read returning nothing; all but the refusal collapse. FalkorDB is the only store, including the scheduler, approvals and dedupe keys.

    Take the graph out

    The same questions, once against FalkorDB and once with every graph read returning nothing. A refusal stays a refusal. This reads what a public channel reads; the admin route at /api/proof is the same report for the terminal.

    The demo, in order

    The script for the company in this graph. Steps that write, or that depend on who is asking, run in Slack; the rest run here too.

    1. who owns billing, and who else has worked on itThe owner, then everyone linked by past work, pull requests and reviews, ranked by their edges to the service.
    2. why did we move the memory layer off postgresThe decision, who proposed and approved it, the RFC and the ticket it is based on, and the decision it superseded.
    3. In Slack: decision: move billing retries to the invoice worker, then ApproveThe card names what the write will replace. The new decision supersedes the old one; asking "why" again shows both, with dates.
    4. what breaks if auth goes down, then and two hops outDependents grouped by hop, the main connector by betweenness, and the route to the invoice worker two hops out.
    5. In Slack: ticket: billing exports time out, Approve, then who should look at itThe ticket is in the graph and the next answer ranks the people connected to that service.
    6. who knows the payments gatewayNot in the graph. The answer says so and names the nearest matches. It never guesses.
    7. The same question from two DMsOnly the teammate whose linked GitHub account can read a private repo sees that repo's pull requests. The permission check is a graph query.

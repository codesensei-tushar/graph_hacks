      How it works

      How an answer is made.

      Three ways in, one fixed catalogue of tools, one graph. Every answer comes back with the path it walked.

      1. 01Resolve.

        Names in the question are matched against the graph first. No match, no guess: it says what it does not know and names the nearest things it does.

      2. 02Pick a tool.

        A fixed catalogue of hand-written, parameterised Cypher. In Slack a model picks the tool and fills in the arguments; it never writes a query.

      3. 03Walk.

        The tool walks the graph, filtered to what the asker may read.

      4. 04Show the path.

        The reply prints every edge it used, A -[REL]-> B. The explanation is the traversal, not a sentence written afterwards.

      • It never writes Cypher.

        The model only fills in the arguments of a tool someone wrote and reviewed. No model-generated string reaches a query.

        tool blast_radius
        args { "name": string, "depth"?: integer }
        runs one fixed, parameterised traversal

      • It refuses to guess.

        A name the graph does not hold is refused, with the nearest names it does hold.

        Nothing in the graph matches “payments gateway” as one thing. Nearest: Billing Service (known as “payments”), API Gateway (known as “gateway”).

      • Writes wait for a human.

        Filing a ticket or recording a decision shows a card that names the target before anything is written.

        Ingest ticket needs approval Review exact action

        The card's wording, pinned by tests/integration/test_slack_agent_turn.py.

      • Decisions stay current.

        A new decision supersedes the old one; both dates stay, and the answer quotes the message it came from.

        New-[SUPERSEDES]->Old

      • Permissions are a graph query.

        Whether someone sees a private repo's pull requests is a path from their Slack account to the repo.

        (:SlackUser)-[:IS]->(:Person)<-[:IS]-(:GitHubUser)-[:CAN_READ]->(:Repo)

      For builders

      The same tools, over MCP.

      Every read-only tool in the catalogue is served at /mcp over streamable HTTP, with the same schemas and the same cited results: the answer, the path, whether it was found, and the nearest names on a miss. Read-only, public scope, no token needed: about 60 calls a minute per address.

      Add it to Claude Code, then ask in plain words; Claude picks the tool.

      claude mcp add --transport http company-brain https://brain.noobsurd.space/mcp

      Streamable HTTP, stateless, JSON responses. No token; a token, where one was issued, lifts the limit.

      https://brain.noobsurd.space/mcp

      The client from the README: list the tools, call one, print the path it walked.

      from mcp.client.session import ClientSession
from mcp.client.streamable_http import create_mcp_http_client, streamable_http_client

async with create_mcp_http_client() as http:
    async with streamable_http_client("https://brain.noobsurd.space/mcp", http_client=http) as streams:
        async with ClientSession(streams[0], streams[1]) as session:
            await session.initialize()
            tools = await session.list_tools()
            result = await session.call_tool("who_owns", {"name": "billing"})
            print(result.structured_content["path"])

      The same answers as plain JSON, the way this page asks: the answer, the tool, the nodes and edges it walked.

      curl -s 'https://brain.noobsurd.space/api/ask?q=who+owns+billing'
